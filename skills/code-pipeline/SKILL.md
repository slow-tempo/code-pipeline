# Code Pipeline

## 간단 버전 (30초 요약)

ponytail(최소 변경) → 얇게 나눠 작성 → codeguard(규칙 스캔) → test-automation(실행, 실패 시 최대 3회 재시도) → code-review(5축 판단) → product-engineer(습관: 관찰 기반 보고). 코드 요청하면 자동 실행, "파이프라인 없이"로 제외. 자명한 수정은 축소판(1→2→4→6), 스파이크는 lite.

## 상세 버전

코드 한 건을 처음부터 끝까지 책임지는 파이프라인. 각 단계의 상세 규칙은 해당 스킬의
SKILL.md를 읽는다. 이 파일은 순서와 생략 규칙만 정한다.

## 자동 적용

코드 작성 요청이 들어오면 사용자가 따로 말하지 않아도 이 파이프라인으로 진행한다.
"파이프라인 돌려줘"라고 명시해도 되고, 그냥 "이 기능 만들어줘"라고 해도 된다.
파이프라인을 원하지 않을 때만 "파이프라인 없이"라고 말한다.

## 단계

1. **ponytail** (작성 전): 7단계 사다리를 타고 최소 변경안을 잡는다. full 기본.
2. **코드 작성**: `incremental-implementation` — 얇게 나눠, 한 조각씩 검증 가능한 상태로.
3. **codeguard** (작성 후): ERR, PERM, DIAG, RES_M 차원으로 스캔.
   DB 없는 프로젝트는 DB 차원 제외. Critical/High는 수정 후 다음 단계로.
4. **test-automation** (실행): 파일 직접 지정 모드로 테스트 실행.
   실패하면 수정 → 재실행, 최대 3회. 3회 초과 시 중단하고 사용자에게 보고.
5. **code-review-and-quality** (완료 전): 5축(정확성·가독성·아키텍처·보안·성능) 리뷰.
   codeguard와 겹치는 지적은 하나로 합친다. codeguard에 없는 performance 차원은 여기서 담당.
6. **product-engineer** (전 과정): outcome 한 문장 재진술 → 관찰 기반 완료 보고 →
   세지 않은 숫자 금지 → 안 만든 것 명시.

## 생략 규칙

- 자명한 수정(오타, 주석, 30줄 미만·로직 무변경): 1 → 2 → 4(해당 테스트만) → 6 축소판.
- 스파이크/실험 코드: 1(lite) → 2 → 6. 프로덕션 승격 시 전체 파이프라인을 다시 돈다.

## 산출물

완료 보고는 `done-means-observed` 형식: 관찰한 것 / 확인하지 못한 것 / 만들지 않은 것.
